# 2026-11-23

## 靜態站搬離 GitHub Pages，改由 Cloudflare Workers Static Assets 供應（15:40）

### 問題現象

`txf.blok.trading` 一直是「Cloudflare 代理 → origin GitHub Pages」。HTML／JSON 雖然有 CF 邊緣快取，但沒命中的請求全打在 GitHub Pages 的 100 GB／月軟限（10 GB／小時）上，滿載 300 人估 158 GB／月會超限。前端 `gh()` 對 `snapshot`／`mis-book`／`imb-*` 走 `no-cache`，更是每次都回源。

### 根因／決策理由

Cloudflare 的 Free／Pro／Business 對 CDN 流量本來就不計費、沒有流量上限，所以「升級方案」解決不了 GitHub Pages 這道牆；唯一解法是把 origin 換掉。

候選三條：

1. Cloudflare Pages（Direct Upload 每 5 分鐘部署）：官方 Pages 總覽寫 Free 方案「500 deploys／月」，社群實測 Direct Upload 不計 build 但官方沒保證。每天 288 次部署會直接踩灰區。
2. Worker + R2 存 data：資料即時、不需重新部署，但要開 R2、改前端路徑、改 Actions 寫入目標，改動面大。
3. **Workers Static Assets**（選這條）：靜態資產請求免費且無上限、Workers Paid 帳號本來就有、沒有每月部署配額、前端路徑與 `gh()` 完全不用改。資料更新靠每次 `wrangler deploy` 的 hash 比對，只上傳變更檔。

### 遺留／已知限制

- 多個 workflow 可能同時部署，後部署者勝；因每次都上傳完整 `public/`，最壞情況是短暫帶到另一邊的舊資料，下一輪自動修正。
- GitHub Pages 仍保留（只做 301 入口）；若日後確認沒人要舊網址，可在 repo settings 關掉。
- `npx` 每次 CI 都要下載 wrangler（約 10–15 秒）；已固定 `4.166.0` 避免版本漂移。

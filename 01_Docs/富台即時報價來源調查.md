# 富台（SGX TWN）即時報價來源調查

> 2026-11-06 實測。目的：台灣期貨休市時，站上要能用富台成交價換算台指點數。
> 結論一句話：**免費源拿不到 24 小時即時；四家券商／資料源只有永豐「差一份 SGX 報價簽署」。**

## 站上目前怎麼做

- 休市模式：`台指期(估) ＝ 富台現價 × 倍數`，倍數＝同時刻的台指 ÷ 富台（1 分 K 配對）
- 富台現價取「時間戳較新」的那個：
  - HiStock 分時 `histock.tw/stock/module/stockdata.aspx?no=TWN`（Worker `?kind=twn` 代理）
  - TradingView 1 分 K 存檔（`scripts/fetch_twn_hist.py` → `data/twn-hist.json`）
- 前端 3.66 起在富台現價旁顯示「N 分前」，超過 15 分轉琥珀色

## 關鍵結論（永豐這條）

- Shioaji 官方支援 Linux，且**行情不需要 CA 憑證**（只有下單要 `activate_ca`）→ 可以上雲
- 卡點在「線上簽署中心 → 期貨類」只有**國外期貨 CME 報價簽署**（已簽），沒有 SGX 那一項
  - 推論（未經營業員或官方文件證實）：缺的就是 SGX 報價授權。已由實測支持的事實只有「TWN 合約在清單裡、snapshot 回 0；同一支 API 抓 TXF 正常」
- 要跟營業員申請：`國外期貨 SGX 報價簽署`，用途＝Shioaji API 抓 SGX 富台（TWN）
- 注意：端點與報價鏈路口的完整對照以 `報價覆蓋契約.md` 附錄A 為單一出處，本檔只記本次結論，不重複一份
- 開通後驗收方式：`api.snapshots([TWN合約])` 的 `close` 不是 0 且 `total_volume` 會動

## 玩股網拆解結果（2026-11-06，最後不採用）

- 商品 id 就是 `stwn&`，頁面路由 `/global/stwn&`
- 目錄：`/investrue/all-alive`（6,654 檔，富台標 `type=Futures`、`country=SINGAPORE`、`fintune=false`）
- 可用端點：`/global/stwn&/historical-realtimeprice-pricemin1-tradedate?tradeDate=<當日 00:00 ms>`
- 會回 400 的端點：`/info`、`/realtimeprice-pricemin1`、`/daily-candlesticks`
- 實測 02:26 抓到 707 根、最後一根 02:22 → 延遲 4.5 分，跨午夜仍有資料
- 但同一支 API 只有住宅 IP（本機）是 200；Cloudflare Worker 400、GitHub Actions 403

- 另：這些端點沒有公開文件，頁面自己標「延遲報價 15 分鐘」（但兩次實測都比它標的快）；既然不採用，就不涉及條款風險

## 更新節奏（2026-11-10 查清）

- `twn-hist.yml` 雖然寫 `cron: "*/5"`，但 2026-11-10 當天 20 筆 run **全部是 `workflow_dispatch`，沒有一筆是 `schedule`**——實際節奏由 Cloudflare Worker 的 `maybeHealTwn()` 控制
- 邏輯：每 2 分鐘（`HEAL_TWN_CHECK_MS`）檢查一次檔案尾端 bar（讀 `twn-hist-meta.json` 小檔），落後超過門檻才 dispatch。門檻＝休市日 10 分（`HEAL_TWN_STALE_MS`）、交易日 30 分（`HEAL_TWN_STALE_IDLE_MS`）；同一根 bar 未推進時受 `HEAL_TWN_RETRY_MS`＝4 分限流
- 交易日實際 dispatch 間隔約 20 分，不是 bug：每次成功都把檔案補到「TV 延遲約 10 分前」，再過 20 分 age 才重新超過 30 分門檻
- 例外（不是穩態）：21:20～21:50 那幾筆間隔只有 9～11 分，是因為抓取連續失敗，尾端 bar 一直不推進，由 `HEAL_TWN_RETRY_MS`＝4 分＋`HEAL_TWN_CHECK_MS`＝2 分的重試節奏補打，不是常態 20 分鐘被打斷
- 因此資料新鮮度上限＝門檻（20～30 分）＋ TV 本身延遲（10～15 分），最壞約 40～45 分。每次都是 4000 根全量，降頻不會漏資料，只影響檔案新鮮度

## WS 端點輪替（2026-11-10）

- 21:20 起 twn-hist 連續失敗，原始 frame 顯示 `data.tradingview.com` 仍回應 session_id／`series_loading`／heartbeat，但**不再推 `timescale_update`**（等於不給歷史資料），前端看起來就是「TV timeout: no bars」
  - 證據 run：`42828181038`（13:50Z，舊版 45 秒 timeout）三次全空等；`42828841699`（13:54Z，TV_DEBUG）逐行 frame 只有 session_id／series_loading／heartbeat
- 同分鐘本機實測：`data.*` 21 秒超時、`prodata.tradingview.com` 0.8 秒、`widgetdata.tradingview.com` 3.3 秒即回 4000 根
- 修法：`scripts/fetch_twn_hist.py` 的 `WS_URLS` 清單＝prodata → widgetdata → data，**每次重試換一個端點**，單次等待 25 秒；`TV_WS_URL` 環境變數可臨時覆寫，`TV_DEBUG=1` 才印原始 frame
- 教訓：先分辨「等不到」是慢還是端點不給，不要直接放寬 timeout（前一版放到 45 秒，21:50 那輪仍三次空等）
